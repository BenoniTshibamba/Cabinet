## 🔴 CRITIQUE

### C1. 18 méthodes `api.*` appelées mais jamais définies dans le bundle de production
**Fichier :** `frontend/js/app.js` — objet `api` (lignes 201-385) vs appels dans le même fichier.

Le `index.html` ne charge que `app.js` (bundle concaténé). Le fichier `frontend/js/api.js` (module ES) contient les méthodes mais **n'est jamais chargé**. L'objet `api` inline du bundle n'a pas été synchronisé : 18 méthodes appelées par l'UI n'existent pas → `TypeError: api.X is not a function` en production.

| Méthode manquante | Appelée (ligne) | Fonctionnalité cassée |
|---|---|---|
| `forgotPassword` | 1373 | Bouton « Mot de passe oublié » |
| `resetPassword` | 1408 | Page de réinitialisation (lien courriel) |
| `twofaStatus` | 1715 | Page paramètres 2FA |
| `twofaSetup` | 1732 | Activation 2FA (QR code) |
| `twofaVerify` | 1749 | Vérification code 2FA |
| `twofaDisable` | 1780 | Désactivation 2FA |
| `twofaLogin` | 1268 | Étape code 2FA à la connexion |
| `oauthGoogleStatus` | 1340 | **Bouton Google ne s'affiche jamais** + `TypeError` non capturée sur la page login |
| `oauthGoogleComplete` | 1448 | Callback OAuth Google (redirige vers login avec erreur) |
| `caseShares` | 3693 | Liste des partages de dossier |
| `shareCase` | 3727 | Partager un dossier avec un avocat |
| `unshareCase` | 3704 | Retirer un partage |
| `deleteUser` | 4529 | Désactivation d'utilisateur (feature v3 !) |
| `lawyers` | 3712 | Liste des avocats (partage de dossiers) |
| `uploadAvatar` | 1840 | Téléversement photo de profil |
| `removeAvatar` | 1823 | Suppression photo de profil |
| `contactMessages` | 4641 | Vue messages de contact (admin) |
| `markContactRead` | 4650 | Marquer message lu/non lu |

**Impact utilisateur :** mot de passe oublié, 2FA complet, login Google, désactivation d'utilisateurs, partage de dossiers, avatars, et messages de contact sont **tous cassés** dans l'UI. Le backend fonctionne (vérifié par appels directs), seul le frontend est touché. La plupart des appels sont enveloppés dans `guarded()` (toast d'erreur), sauf `oauthGoogleStatus()` ligne 1340 qui lève une `TypeError` synchrone non capturée.

**Cause racine :** `app.js` est un bundle maintenu à la main ; sa section `/* --- api.js --- */` n'a pas été mise à jour quand les méthodes ont été ajoutées à `frontend/js/api.js`. Les deux fichiers ont divergé dans les deux sens (ex. le bundle a `askAI(question, caseId, lang)` avec `lang`, `api.js` ne l'a pas).

**Correctif :** recopier les 18 définitions depuis `frontend/js/api.js` dans l'objet `api` du bundle (lignes 201-385), retester, redéployer. À terme : mettre en place une vraie étape de build (ou supprimer `api.js`/`session.js`/`dom.js`/`icons.js` et ne maintenir que le bundle).

**Couverture tests :** NON couvert. Les tests vérifient le backend uniquement. Recommandation : ajouter un test statique qui parse `app.js` et vérifie que toute méthode `api.X(` appelée est définie dans l'objet `api`.

## 🟠 MAJEUR

### M1. Aucun flux d'approbation des demandes d'accès
**Fichiers :** `backend/src/routes/registration.js`, `frontend/js/app.js`.

- Backend : `POST /registration-requests` (soumission) et `GET /registration-requests` (liste admin) existent, mais **aucun endpoint d'approbation/rejet**.
- Frontend : seule la soumission existe (`registerRequest`, ligne 353). Aucune UI pour voir ou traiter les demandes.
- La notification `REGISTRATION_REQUEST` mène vers `#/dashboard` (aucune action possible).

**Impact :** un visiteur demande l'accès → l'admin est notifié → **l'admin ne peut rien faire**. Il doit créer le compte manuellement via la page Utilisateurs.

**Correctif :** ajouter `PATCH /registration-requests/:id` (`{ status: 'APPROVED'|'REJECTED' }`, créant l'utilisateur si approuvé) + page admin « Demandes d'accès ».

**Couverture tests :** partielle — le test « demandes d'accès — notification admin » (ligne 1939) vérifie seulement la création de la notification, pas l'approbation.

### M2. Fichiers sources morts et divergents
**Fichiers :** `frontend/js/api.js`, `frontend/js/session.js`, `frontend/js/dom.js`, `frontend/js/icons.js`.

Modules ES jamais chargés par `index.html` (qui ne charge que `theme-init.js`, `i18n.js`, `contact-mailto.js`, `app.js`). Ils ont divergé du bundle dans les deux sens (C1 en est la conséquence). Source de confusion et de bugs futurs.

**Correctif :** soit implémenter un build qui génère `app.js` depuis ces fichiers, soit les supprimer et documenter que `app.js` est la seule source de vérité.

## 🟡 MINEUR

### m1. Permission `contact.read` utilisée pour une écriture
**Fichier :** `backend/src/routes/contact.js:101` — `PATCH /:id` (marquer lu/non lu) exige `contact.read` au lieu d'une permission d'écriture. Fonctionne (seuls les admins ont `contact.read`), mais sémantiquement incorrect. Pas de `contact.update` dans `utils/permissions.js`.

### m2. Le mailer avale silencieusement les erreurs
**Fichier :** `backend/src/services/mailer.js:33-41` — `sendMail()` ne rejette jamais, loggue seulement en console. Voulu par design, mais rend le diagnostic SMTP impossible depuis l'UI (constaté le 2026-10-11 : l'endpoint `/auth/forgot-password` répondait 200 sans que le courriel parte). Recommandation : exposer un endpoint admin de test SMTP ou, au minimum, un compteur d'échecs.

## Vérifié et sain

- **Authentification** : login, refresh avec rotation, logout, `requireAuth` (vérifie `is_active` à chaque requête → un compte désactivé perd l'accès immédiatement malgré un JWT valide), 2FA TOTP (setup/verify/disable/login), OAuth Google (vérification `email_verified`, restriction aux comptes existants, 2FA respecté après OAuth).
- **Désactivation utilisateur** : garde-fous self / dernier super-admin / dossiers assignés, révocation des refresh tokens.
- **RBAC** : `requirePermission` fail-closed (403 sans `req.user`) ; tous les routeurs sensibles ont `router.use(requireAuth)` ou une protection par route ; les routes publiques (blog, contact, inscription) sont intentionnelles.
- **Documents** : upload avec type/taille limités, nom de fichier aléatoire (anti path-traversal), suppression, téléchargement authentifié.
- **Messagerie** : pièces jointes vérifiées (auteur + membre de conversation), `assertDocReadable` pour les documents joints.
- **i18n** : 720 clés FR + 720 clés EN, aucune manquante des deux côtés.
- **Ordre des routes Express** : vérifié (pas de capture prématurée par `:param`).
- **Formes de réponse** : `issueSession` retourne `{ accessToken, refreshToken, user }` comme attendu par le frontend.
- **Déploiement** : `render.yaml` + `Dockerfile` cohérents (disque persistant, `DATABASE_PATH`, `UPLOAD_DIR`, `healthCheckPath`).
